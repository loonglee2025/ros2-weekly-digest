# ROS2 技术周报 — 2026-07-20 至 2026-07-26

## 总判断

本周是 ROS 社区生态活跃度非常高的一周，核心信号集中在三个方向：**RMW 路线的 Python 原生突破**（PyZeROS）、**基础设施可观测性上线**（Buildfarmer Dashboard）、以及 **Nav2 平台基准测试开源**。这三个事件分别对应框架层、工程层和应用层，说明 ROS2 正在从"能不能用"的阶段走向"如何更高效、更可观测、更可衡量地用"的阶段。此外，本周 Katherine Scott 的社区周报涵盖大量新项目发布，AMD 边缘计算设备支持扩展、NVIDIA Jetson 涨价引发的硬件替代讨论也值得持续跟踪。

## 本周关键信号

### 1. PyZeROS 发布：Python 原生 ROS2 客户端，5.5× 性能超越 rclpy

**发生了什么：** 开发者 Elian Neppel（@2lian）发布 PyZeROS，一个纯 Python 编写的 ROS2 客户端库，通过 Zenoh RMW 与标准 ROS2 节点互操作。可 `pip install pyzeros`，无需 ROS 安装、colcon workspace 或消息编译。

**为什么值得关注：** 这是 ROS2 Python 生态多年来第一个真正意义上的 rclpy 替代方案。核心差异：
- 纯 `pip` 安装，天然支持 venv/uv/pipx
- 消息类型可直接用 Python dataclass 定义，无需 `.msg` 文件 + colcon build
- 原生 `asyncio` 架构，空消息往返延迟仅 **12 µs**（rclpy SingleThreadedExecutor ~70 µs），负载场景 CPU 仅 rclpy 的 1/4
- 与 Lyrical 的新 `AsyncNode` 对比：小消息 AsyncNode 略快（10 µs），复杂消息 PyZeROS 反超（16 µs vs 22 µs）

**影响层面：** RMW 层 / 核心框架层

**下一步关注：** ROSCon 上 rclpy AsyncNode 团队（@nadavelkabets）的正式演讲；PyZeROS 的社区采纳度及与 rclpy 的集成兼容性讨论

### 2. Buildfarmer Dashboard 上线：ROS & Gazebo CI 健康状况一站可见

**发生了什么：** OSRF 基础设施团队发布了公开的 Buildfarmer Dashboard，汇总 ROS 和 Gazebo 的 CI 回归信息，包括：活跃测试回归（首次失败日期、受影响平台、关联 issue）、Flaky 测试（滚动窗口内的失败率与跨平台签名）、可疑提交（最后一次成功到首次失败的 git compare 链接）、已知问题状态。

**为什么值得关注：** 此前获取 CI 健康状态需要直接联系 buildfarmer 或在仓库 issue 中搜索。Dashboard 将这一过程变为自助服务，大幅降低了贡献者的调试门槛。这是 ROS 基础设施可观测性的重要里程碑。

**影响层面：** 工程化 / CI 基础设施层

**下一步关注：** Dashboard 的反馈迭代（社区已提出 flaky test 阈值问题）；Windows 平台的持续回归问题

### 3. Nav2 / Open Navigation 开源机器人工作负载基准测试

**发生了什么：** Steve Macenski 发布了首个面向真实机器人负载的计算平台基准测试。测试场景：在 180,000 sqft 仓库中用完整自主栈执行叉车取放任务，处理 9 个传感器流（3D LiDAR、深度相机等），同时运行重型 VLM 工作负载。已基准平台包括 AMD Strix Halo、NVIDIA Jetson Thor 和 Orin AGX。

**为什么值得关注：** 这是社区首个基于完整自主栈（而非孤立微基准）的硬件评测工具，且完全开源、Docker 化。结合本周 NVIDIA Jetson 全线涨价 50-100% 的讨论，该基准为行业选择替代平台（尤其是 AMD Kria AI）提供了数据支撑。

**影响层面：** 应用层 / 工程化层

**下一步关注：** AMD Kria AI 平台定价信息；社区贡献的其他平台测试结果

### 4. ros2log：ROS2 CLI 的新包引入

**发生了什么：** Tomoya Fujita 提交了 `ros2log` 新包到 ros2cli 仓库（PR #1217），旨在为 ROS2 提供更好的日志管理 CLI 工具。

**为什么值得关注：** ros2cli 的新子命令通常意味着 ROS2 开发者体验的改进方向。日志管理是实际工程中的高频需求。

**影响层面：** 工具链层

### 5. roschema：在 CI 中捕获破坏性 .msg/.srv/.action 变更

**发生了什么：** Saif Sidhik 发布了 `roschema` 工具，可在 CI 阶段检测消息定义变更是否破坏兼容性。

**为什么值得关注：** 消息兼容性断裂是 ROS 多包协作中最隐蔽的问题之一。该工具填补了自动化检测空白，对大型团队协作意义重大。

**影响层面：** 工程化层

### 6. NVIDIA Jetson 涨价 50-100%，社区热议替代平台

**发生了什么：** Discourse 上关于 Jetson 涨价的讨论获得 333 次浏览和 7 个 like。社区成员分享了多种替代方案，Steve Macenski 参与讨论。

**为什么值得关注：** 这不仅是硬件选型问题，更可能影响 ROS2 边缘部署的硬件生态格局。AMD Kria AI 的同期发布时机非常微妙。

**影响层面：** 硬件 / 部署层

## 核心框架更新

### Rolling Nightlies

Rolling 仓库继续每日构建（nightlies 2026-07-26），Lyrical 发布后 Rolling 保持与 Lyrical 同步状态，无独立新发行版公告。

### rclcpp

- **恢复 `cassert` 直接包含**（PR #3212，Tyler Gibbs）：修复因间接依赖变化导致的编译失败，属于构建兼容性修复
- **限定 `ShutdownCallbackHandle` 作用域**（PR #3208，Tobias Fischer）：在 `context.cpp` 中显式使用 `rclcpp::ShutdownCallbackHandle`，提升代码健壮性

### rclpy

- **Lifecycle 节点回调异常处理**（PR #1696，Sai Kishor Kothakota）：在 lifecycle transition 回调中增加了异常捕获机制，防止未处理异常导致节点状态不一致

### rosbag2

- **RMW 测试隔离运行**（PR #2460，yadunund）：在独立环境中运行 RMW 测试，错误时调用 shutdown，避免测试间污染
- **文档修复：Reader 用法示例**（PR #2455，Jakub Gawlik）

### ros2cli

- **`ros2log` 新包引入**（PR #1217，Tomoya Fujita）：新的日志管理 CLI 命令

### RMW 层

- **rmw_fastrtps**：修复 `buffer-aware subscriptions` 在 `rmw_wait` 调用间保留未读数据的问题（PR #900，CY Chen）
- **rmw_cyclonedds**：修复 subscription graph cleanup 在销毁时的资源释放问题（PR #594，ganla）

### Gazebo（gz-sim）

- **SwerveDrive 系统插件**（PR #3365，Jiayi Cai）：新增全向底盘系统插件
- **四元数符号翻转导致角速度尖峰修复**（PR #3834，Bong）
- **传感器示例修复**（PR #3848，cheriehu）
- **Protobuf 类型转换替换**（PR #3743，ClaytonKnittel）

## 工程化观察

### 本周最值得关注的工程化进展

1. **Buildfarmer Dashboard 上线**：此前开发者和贡献者排查 CI 失败需要手动搜索 issue 或联系 buildfarmer，现在是自助服务。这是 ROS 基础设施可观测性从"人工驱动"到"数据驱动"的关键转变。

2. **roschema 填补消息兼容性检测空白**：`.msg`/`.srv`/`.action` 的 breaking change 是 ROS2 多包协作中最隐蔽的陷阱之一，该工具将检测前移到 CI 阶段。

3. **rmw_fastrtps 的 buffer-aware subscription 修复**：这个 bug 可能导致订阅者在 rmw_wait 调用间丢失未读数据，对实时性要求高的系统影响较大。

### 回归与风险提示

- **Windows 平台 CI 回归**：Dashboard 数据显示 Windows 仍是 CI 回归最多的平台，社区反馈指出需要更多关注
- **Gazebo flaky test 阈值问题**：Dashboard 当前可能漏报部分已知 flaky tests（如 ApplyLinkWrenchTestFixture 和 PeerTracker），社区建议调整阈值

## 前沿议题

### 1. PyZeROS + Zenoh：Python 生态与 ROS2 的新接口范式

PyZeROS 的意义不仅是"又一个 rclpy 替代品"。它展示了纯 Python + Zenoh 这条路径的可行性：无需 C 扩展、无需 colcon、天然支持现代 Python 工具链。如果这条路线成熟，将显著降低 ROS2 在数据科学、AI/ML 集成场景中的使用门槛。值得注意的是，PyZeROS 的基准测试显示它比 rclpy 快 5.5× 且 CPU 仅 1/4，说明当前 rclpy 的 Python-C 桥接层存在显著性能损耗。

### 2. 计算平台选择：Jetson 涨价 vs AMD Kria AI

NVIDIA Jetson 涨价 50-100% 是本周社区最热门的硬件话题。AMD 同步发布的 Kria AI 平台在 Nav2 基准测试中表现强劲。这不仅是价格问题，更可能改变 ROS2 边缘部署的硬件生态格局。Steve Macenski 的基准测试工具为此提供了客观比较依据。

### 3. ZeroDDS（纯 Rust RMW）仍在活跃讨论

前几周发布的 ZeroDDS rc.3 本周仍有新讨论（245 次浏览，9 likes），社区对 Rust 实现 RMW 路线的兴趣持续。这与 PyZeROS 的纯 Python 路线形成有趣的对比——社区正在探索多种语言原生实现 ROS2 客户端的可能性。

## 可继续深挖的问题

1. **PyZeROS 与 rclpy AsyncNode 的性能对比**：目前的数据还局限在微基准层面。需要更多实际场景（多节点、高频率、跨进程）的对比数据，以及 PyZeROS 在长期运行中的稳定性验证。

2. **Buildfarmer Dashboard 的 flaky test 判定阈值**：社区已反馈部分已知 flaky test 未被 Dashboard 捕获，阈值设定是否过严？需要跟踪 Dashboard 的后续迭代。

3. **AMD Kria AI 的实际定价与可用性**：Nav2 基准测试显示其性能与 Orin AGX 相当，但定价信息尚未公布。需持续跟踪。

4. **ZeroDDS 与 PyZeROS 的路线交叉点**：ZeroDDS 是 Rust RMW，PyZeROS 是纯 Python + Zenoh。两者是否可能形成互补？Zenoh 作为中间层的地位是否会因此强化？

5. **`ros2log` 的具体能力边界**：PR 尚在 review 阶段，其最终功能集和对现有日志工具（如 `rqt_console`）的影响需在合并后评估。
