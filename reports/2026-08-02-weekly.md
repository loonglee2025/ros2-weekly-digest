# ROS2 技术周报 — 2026-07-27 至 2026-08-02

## 总判断

本周 ROS 2 的主旋律是**「执行器架构统一、工程化与工具链持续补课、Python 与实时两条路线并行推进」**。最重磅的信号是 skye.galaxy 提出 `rcl_executors` 统一执行器包，意图把 rclcpp/rclpy 中重复且维护成本高的 7 种 executor 收敛为以 `EventsCBGExecutor` 为核心的单一参考实现；同日 esol-community 发布的 `ros2_realtime_support` 独立包则代表另一条路线：不改核心库，用外部包提供实时线程属性与专用执行器。两条路线并存，说明 ROS 2 正在同时解决「代码臃肿/行为不一致」和「实时性可落地」两个长期痛点。与此同时，社区围绕 uv/venv 工作流、Buildfarmer Dashboard 改进、Nav2 碰撞监控增强等议题持续推进工程化细节。整体来看，本周变化偏「结构性」而非「发布密集」，但对未来两年的框架形态有深远影响。

## 本周关键信号

### 1. 提出 `rcl_executors`：统一所有 client library 的参考执行器包

**发生了什么：** skye.galaxy 在 Discourse 发布长篇提案，指出 rclcpp 与 rclpy 当前共有 7 种 executor（SingleThreaded、MultiThreaded、EventsCBG、EventsExecutor、rclpy 实验性 EventsExecutor、rclrs executor 等），彼此代码重复、行为差异大、维护困难。提案建议：
- 将核心执行器实现去重并迁移到新的 C++ 包 `rcl_executors`
- 保持 `rcl` 为纯 C 包，不引入 C++ 到嵌入式场景
- 让 `rclcpp::executors::EventsCBGExecutor` 成为 `rcl_executors::EventsCBGExecutor` 的别名
- `rclpy` 仅负责 pybind（或 nanobind）该执行器，不再维护独立实现
- 将 `rclcpp::spin()` / `rclpy.spin()` 默认实例化为 `rcl_executors::EventsCBGExecutor`
- 在 m-turtle 中弃用、n-turtle 中移除基于 wait-set 的 `SingleThreadedExecutor` / `MultiThreadedExecutor`

**为什么值得关注：** 这是自 Lyrical 引入 `EventsCBGExecutor` 以来最大的一次执行器架构重构设想。如果落地，意味着 ROS 2 将正式从「wait-set 轮询」时代走向「事件驱动 + 回调组」时代；rclpy 性能长期受限于自研 C++ 执行器的局面也可能得到根本性缓解。gbiggs 在回帖中强调，把 `rcl` 保持为纯 C 包对 micro-ROS / rclc 很重要；scastro 则呼吁借此机会把绑定库从 pybind11 升级到 nanobind。

**影响层面：** 核心框架层 / 所有 client library（rclcpp、rclpy、rclrs、rclc）

**下一步盯什么：** 该提案是否进入 WG 讨论并形成 REP；`rclpy` 绑定方式（pybind vs nanobind）的取舍；对自定义 `Waitable` 的兼容性影响评估；旧 executor 迁移/别名方案是否会造成用户代码静默行为变化。

### 2. `ros2_realtime_support` 独立包发布：不改 rcl/rclcpp 的实时支持路径

**发生了什么：** eSOL（esol-community）发布 `ros2_realtime_support` 包，将过去几年的 rcl/rclcpp 实时增强工作改为**独立包**实现。其做法：
- 提供 `rclcpp_realtime` 命名空间，替换 `rclcpp::init` / `rclcpp::shutdown` 等入口
- 通过 YAML 配置或 `--ros-args` 指定线程属性（调度策略、优先级、CPU affinity 等）
- 为 executor 提供线程属性，允许在不改动 rclcpp 源码的情况下实现实时调度

**为什么值得关注：** 这代表了一种与 `rcl_executors` 提案互补的推进方式：核心框架保持精简，实时能力通过扩展包叠加。发布者明确提到，过去在 PTC 会议上被指出「在 rcl 中增加实时功能会提高发布测试和 OS 支持成本」，因此改为独立包。该路线降低了实时特性进入 ROS 主线的阻力，也减少了 Lyrical/Rolling 用户被强制绑定实时相关依赖的风险。

**影响层面：** 实时系统 / 控制层 / 嵌入式与工业应用

**下一步盯什么：** 该包与 `rcl_executors::EventsCBGExecutor` 是否能协同工作；后续是否会把 rclcpp 中的 mutex/condition_variable 替换为 RTOS 原生 API；单 PC 上 intra-process 通信的实时性保证仍是未解问题。

### 3. uv + ROS 2 工作流实战报告：5 个失败模式与 colcon/ament 最小改动提案

**发生了什么：** Decwest 在 Discourse 发布「uv on ROS 2」的实战报告，基于 Ubuntu 24.04 + Jazzy + Python 3.12 + uv 0.11.28 的真实机器人栈迁移经验，梳理了五个 reproducible 失败模式：
- 每次 shell 需要同时 `source setup.bash` 和激活 venv
- colcon 会把 venv 子目录当作包发现
- `ros2 run` 在 venv 激活时仍使用系统 Python 解释器（`--symlink-install` 下无完整 workaround）
- numpy 2.x 与 apt 编译的 cv_bridge 等 C 扩展 ABI 不兼容
- uv 默认使用独立 CPython，与系统编译的 C 扩展 ABI 不匹配

并给出三个最小改动提案：
- P1：colcon 发现时自动跳过含 `pyvenv.cfg` 的目录
- P2：统一提供选项让 install 和 develop 路径都生成 `#!/usr/bin/env python3` shebang
- P3：在 `install/` 中记录 colcon 使用的解释器，让 `setup.bash` 自动激活对应 venv（opt-out）

**为什么值得关注：** 这是 PEP 668 + Ubuntu 24.04 之后，ROS 2 Python 开发者最切肤的痛点的系统性总结。它不仅提出 workaround，还给出了**不破坏现有工作流**的 colcon/ament 改进方向，与 PyZeROS / rclpy AsyncNode 等纯 Python 路线形成「底层工具链」与「上层客户端库」的呼应。

**影响层面：** 工具链 / Python 开发体验 / 依赖管理

**下一步盯什么：** 三个提案是否进入 colcon-core 讨论；PyZeROS 的纯 Python 路线是否会绕过这些 colcon 问题；官方文档是否会更新为 PEP 668 时代提供 venv 工作流最佳实践。

### 4. Fast-CDR v2.4.0 发布：严格 bool 规范化与序列化上下文

**发生了什么：** eProsima 发布 Fast-CDR v2.4.0，主要新增：
- `STRICT_BOOL` CMake 选项，对 bool 进行严格规范化（避免 vector<bool> 序列化时的历史歧义）
- `Cdr` 对象支持上下文（context）概念
修复：
- 序列化 vector<bool> 为数组时不再设置 `SERIALIZED_MEMBER_SIZE`
- 改进序列长度检查

**为什么值得关注：** Fast-CDR 是 Fast DDS 的底层序列化库，也是 ROS 2 默认 RMW 的依赖。bool 序列化与 vector<bool> 是 DDS/ROS 2 类型兼容性中常见的隐形坑，`STRICT_BOOL` 的引入可能影响跨版本/跨平台的消息兼容性。工程上需要关注该选项是否会被默认启用，以及是否会导致与旧版本 Fast-CDR 的互操作问题。

**影响层面：** RMW 层 / 中间件层 / 消息序列化兼容性

**下一步盯什么：** Fast-CDR v2.4.0 何时进入 Rolling/Lyrical 的 sync；`STRICT_BOOL` 默认是否开启；下游 ROS 2 包是否需要重新测试兼容性。

## 工程化观察

1. **执行器统一与实时独立化并行**：`rcl_executors` 提案和 `ros2_realtime_support` 独立包看似方向不同，实则互补——前者解决「多 client library 重复实现、行为不一致」的代码组织问题，后者解决「核心库不愿承担实时支持成本」的部署问题。两者共同说明 ROS 2 正在进入「核心更精简、扩展更专业」的模块化阶段。

2. **Python 工具链补课是持续主题**：从 PyZeROS（前几周）、rclpy AsyncNode、到本周的 uv/colcon 工作流提案，ROS 2 Python 生态正在从「能用」走向「与 Python 原生工具链兼容」。需要关注 colcon/ament 是否接受 P1/P2/P3 提案，以及这是否会让官方更积极推动「workspaces as venvs」。

3. **Fast-CDR 的 bool 规范化需兼容性评估**：`STRICT_BOOL` 默认关闭时是安全升级；如果未来 Rolling/Lyrical 的 Fast-CDR 默认开启，需要重新验证与旧二进制/旧 DDS 实现的互操作。建议跟踪 rosdistro 中 fastcdr 的版本 bump 公告。

4. **Lyrical 分支分离进入高峰期**：Nav2 完成 branch off 意味着多个生态项目正从 Rolling 中切出 Lyrical 稳定分支。接下来几周是 sync 和回归修复的密集期，应重点关注各项目是否宣布 Lyrical 兼容版本或 CI 回归。

5. **Buildfarmer Dashboard 与 buildfarm 升级联动**：Dashboard 刚上线即遇到基础设施维护，说明 CI 数据链路还在磨合。建议在 Jenkins 升级后重新观察 Dashboard 数据连续性和 flaky test 阈值反馈。

## 前沿议题

### 1. `rcl_executors` 的 nanobind 与 asyncio 路线之争

`rcl_executors` 提案中，scastro 提出用 nanobind 替代 pybind11，而 2lian（PyZeROS 作者）再次强调 executor 应该交给语言原生机制（asyncio）。这两条路线可能塑造未来 rclpy 的形态：是继续绑定一个统一的 C++ 执行器，还是让 Python 开发者直接基于 asyncio 与 RMW 通信。后者的工程意义在于减少 Python-C 桥接层，但前者在实时性和多语言一致性上仍有优势。

### 2. ROS 2 与 AI 的边界继续模糊

本周 Discourse 上「AI 辅助贡献指南」帖持续升温（3d 内更新），同时 QERRA-v2（伦理安全中间件）和 ros2_lingua（LLM grounding）等社区项目也在讨论区活跃。AI 不再只是生成文档和代码，而是开始出现在运行时安全校验、行为树规划和能力注册等场景。PMC 的「AI 贡献指南」与这些运行时工具之间的治理边界，可能会成为未来争议点。

### 3. OpenUSD / 仿真资产互操作性（REP 158）仍在发酵

REP 158 草案帖持续收到评论，讨论 OpenUSD 作为仿真资产交换格式的命名约定、单位与坐标系一致性。该议题对 Gazebo、Isaac、Unreal 等多仿真平台协同工作流至关重要，但进展偏慢，预计需要多次 PMC 审议。

5. **Nav2 Lyrical branch off 后是否引入新的 API 破坏点？** 需要比对 Rolling 与 Lyrical 分支的 changelog，尤其是 BT.CPP 版本解绑后的行为变化。

6. **Buildfarm Jenkins 升级后 Dashboard 数据连续性如何？** 建议在 2026-08-03 停机后观察是否有数据断点或回归误报。
