### [](http://discourse.ros.org/t/ros-pmc-minutes-for-september-1st-2026/57808/print#p-117486-buildfarm-update-3)Buildfarm update

The buildfarm builds and tests ROS packages across all supported distributions and platforms. This section covers new issues, current priorities, and infrastructure changes that affect maintainers.

*   ![Image 1: :chart_increasing:](https://emoji.discourse-cdn.com/noto/chart_increasing.png?v=15)**New greenness report.** Greenness is generally down this month other than Lyrical, though the headline number counts only fully green builds and not yellow ones. The expanded report behind the month number gives the fuller picture. 
    *   Rolling has some green this month, in the low double digits. Not good in absolute terms, but the trend is in the right direction.
    *   Zenoh is green again, after sustained effort from [@yadunund](http://discourse.ros.org/u/yadunund) and [@ahcorde](http://discourse.ros.org/u/ahcorde).

*   ![Image 2: :new_button:](https://emoji.discourse-cdn.com/noto/new_button.png?v=15) Issues 
    *   `zenoh_cpp_vendor` Cargo.lock and `OPAQUE_TYPES_BUILD_DIR` warnings, Windows only. A warning rather than a regression. [@mjcarroll](http://discourse.ros.org/u/mjcarroll) has taken it and will try to reproduce locally.
    *   **Windows 11 `ros2_multicast``test_api` regressions on release jobs**, which had appeared in 2025 and have started again. Presents as a buffer space fault affecting a large number of multicast tests. 
        *   Working hypothesis is that SIGTERM-based teardown on Windows leaves resources behind and we eventually exhaust multicast sockets on the host.
        *   [@claraberendsen](http://discourse.ros.org/u/claraberendsen) hit the same wall on Windows during Lyrical work. Because Windows uses process isolation rather than full containers, sequential runs share the underlying networking on the host, so incomplete cleanup accumulates. Reviewing the agent’s build log showed it had run nightly repeated jobs for at least five days in a row, so this may be a combination of repeated runs on one agent and cleanup not doing enough.
        *   [@MiguelCompany](http://discourse.ros.org/u/miguelcompany) noted that exiting cleanly rather than terminating would close sockets, and ruled out parallelism as a cause: nightlies run packages in parallel, but these tests are all within a single package and therefore sequential.
        *   [@clalancette](http://discourse.ros.org/u/clalancette) pointed out we already do some cleanup, killing stray colcon processes and similar, and that it could be made more extensive, though a run may also be conflicting with itself rather than inheriting a bad state.
        *   [@mjcarroll](http://discourse.ros.org/u/mjcarroll) will look at extending the CI cleanup pass and whether there is an internal fix.

    *   Warning on ignoring the return value of `rmw_ret_t`, affecting all Linux builds including RHEL and aarch64. Traced to a test merged into an RMW implementation two days ago; clang is stricter about this. [@miguelgonrod](http://discourse.ros.org/u/miguelgonrod) will open the issue and ping the author, and it should be an easy fix.

### [](http://discourse.ros.org/t/ros-pmc-minutes-for-september-1st-2026/57808/print#p-117486-rosdistro-assignmentshttpsgithubcomrosrosdistro-5)[Rosdistro assignments](https://github.com/ros/rosdistro)

Rosdistro is a weekly assignment to monitor incoming issues and pull requests in [GitHub - ros/rosdistro](https://github.com/ros/rosdistro). Two people per week are assigned to be the rosdistro maintainers.

*   Sep 1, 2026 - Sep 8, 2026 
    *   [@clalancette](http://discourse.ros.org/u/clalancette)
    *   [@sloretz](http://discourse.ros.org/u/sloretz)

*   Generally in good shape at around 11 open pull requests, which is about as good as it has looked.
*   **[rosdistro#53263](https://github.com/ros/rosdistro/pull/53263): an aggregated collection of example robot URDFs.** This started as a naming and licensing question and broadened considerably. 
    *   [@christophebedard](http://discourse.ros.org/u/christophebedard) flagged the name as too generic and suggested prepending the originating lab’s name. The contents turn out to be directories rather than individual packages, so this is a single package aggregating copies of others.
    *   [@clalancette](http://discourse.ros.org/u/clalancette) raised the more fundamental question of whether we should take it at all, since it conflicts with the originals such as `ur_description` and `human_description`, and a copy will inevitably drift from upstream. The repository itself states it does not intend to substitute for the original repositories, which invites the question of what it is for. Rosdistro is a curated set more like a Linux distribution than an open-upload index.
    *   [@sloretz](http://discourse.ros.org/u/sloretz) noted we have accepted generic names before, particularly around interface definitions, where maintainers commit to stewarding the name and accepting contributions broadly. That would be a reasonable condition here.
    *   [@yadunund](http://discourse.ros.org/u/yadunund) and [@christophebedard](http://discourse.ros.org/u/christophebedard) both objected to “data”, since these are descriptions, and to “example”, since the contents are named commercial robots rather than illustrative ones. It reads more like an awesome-list.
    *   Alternatives raised: a ROS metapackage, or simply a documentation pull request listing the resources.
    *   [@emersonknapp](http://discourse.ros.org/u/emersonknapp) made the broader point that **we have no stated content guideline or quality bar**, so we relitigate this case by case. We should either state a policy or accept that we do not have one.
    *   **Actions:**[@mjcarroll](http://discourse.ros.org/u/mjcarroll) to draft rough content guidelines for rosdistro submissions. [@clalancette](http://discourse.ros.org/u/clalancette) to comment on the pull request as part of rosdistro duty this week.

## [](http://discourse.ros.org/t/ros-pmc-minutes-for-september-1st-2026/57808/print#p-117486-agenda-8)Agenda

*   [[@clalancette](http://discourse.ros.org/u/clalancette)] **[rosbag2#2476](https://github.com/ros2/rosbag2/pull/2476): playing bags with mixed serialization formats**
    *   The change removes two virtual methods from `SequentialReader`, which is technically an API break for subclasses. No users of those overrides could be found anywhere in Rolling. The change targets Rolling only and will not be backported; if it were, the methods would be kept as dead stubs.
    *   [@emersonknapp](http://discourse.ros.org/u/emersonknapp) confirmed no meaningful use of that path. [@MiguelCompany](http://discourse.ros.org/u/miguelcompany) suggested pinging @morlov in case of private work inheriting from it, and [@clalancette](http://discourse.ros.org/u/clalancette) will do so.
    *   The change adds a `serialization_format` field to `rosbag2_storage::SerializedBagMessage`. The open question was whether to also add one to `rclcpp::SerializedMessage`, which would matter for something like protobuf serialization in the core later. **Consensus: keep it scoped to rosbag2 for now**, with the wider change as a possible follow-up.
    *   [@tomoyafujita](http://discourse.ros.org/u/tomoyafujita) is reviewing. Further reviews welcome.

*   [[@MiguelCompany](http://discourse.ros.org/u/miguelcompany)] **[rmw_fastrtps#906](https://github.com/ros2/rmw_fastrtps/pull/906): pinning dependency versions**
    *   Motivation: an ABI break in the shared package meant that someone who updated only `rmw_fastrtps` had everything break underneath them.
    *   [@cottsay](http://discourse.ros.org/u/cottsay) flagged that this creates two things to keep in sync, and our release automation does not update the pins. colcon will warn when versions drift, and buildfarm RPMs respect the constraint, but whether the Debian packages do needs checking, and `catkin_pkg` prepare-release will not maintain it. That becomes painful at release time across hundreds of packages.
    *   [@clalancette](http://discourse.ros.org/u/clalancette) suggested a greater-than constraint rather than an equality one, so packages are not dead on arrival, and noted this is a stack-wide problem rather than anything specific to Fast DDS.
    *   [@cottsay](http://discourse.ros.org/u/cottsay) proposed a better general avenue: **package format 3 already has a version compatibility flag that we largely do not use.** Properly plumbed through, a package’s dependencies could be locked to the versions it was built against and enforced in the downstream Debian and RPM packages, making a piecemeal update that breaks your system impossible. He offered to work with [@MiguelCompany](http://discourse.ros.org/u/miguelcompany) on solving this broadly.
    *   [@MiguelCompany](http://discourse.ros.org/u/miguelcompany) will comment on the PR regarding the compatibility flags and iterate from there.
