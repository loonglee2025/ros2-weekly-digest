## [](https://discourse.ros.org/t/x/57646#p-117240-background-2)Background

[Open-RMF](https://www.open-rmf.org/) coordinates fleets of different robots that share the same building. The project is moving away from a monolithic stack toward the “horizontal” architecture described in the [next-generation roadmap](https://discourse.openrobotics.org/t/next-generation-open-rmf-roadmap/53820). In this design, smaller ROS 2 nodes communicate through well-defined messages and can be replaced independently.

The [`next_gen_prototype`](https://github.com/open-rmf/next_gen_prototype) repository is the reference implementation of that design. It currently has a **Destination Server**, which decides whether a robot can claim a destination; a **Path Server**, which handles multi-agent path finding; and a **Plan Executor**, which moves a robot along the resulting plan.

My work focused on two missing pieces from [issue #8](https://github.com/open-rmf/next_gen_prototype/issues/8):

1.   A reservation-aware destination server that can queue a robot when its requested destination is already occupied.
2.   A layered global occupancy map that shares obstacles detected by individual robots with the central planner, allowing the fleet to replan around them ([issue #27](https://github.com/open-rmf/next_gen_prototype/issues/27)).

The nodes are written in Rust using `ros2_rust`. Python is used for launch files, demos, and tests.

## [](https://discourse.ros.org/t/x/57646#p-117240-h-1-reservation-aware-destination-server-3)1. Reservation-aware destination server

**[PR #25](https://github.com/open-rmf/next_gen_prototype/pull/25)**, +9,096 / −55 across 37 files, merged 1 July 2026

The previous setup used a simple destination server, where if a requested goal overlapped an existing goal reserved by another robot, the request failed and the requesting robot stopped. This is a common situation around shared resources, so we added the reservation destination server as an optional replacement. Users can choose between the two servers at launch.

With the reservation server, we introduce the concept of parking zones: user-defined areas where robots can wait when their requested goal is already claimed. Users can place these zones wherever they make sense for the site—for example, in out-of-the-way corners where waiting robots will not block traffic, or at charging stations where they can recharge while they wait. During operation, if several robots request the same goal, the server sends those that cannot proceed to available parking zones and keeps their original requests queued.

[![Image 1: reservation](https://us1.discourse-cdn.com/flex022/uploads/ros/optimized/3X/2/9/2970bdeadc1a7726593c1bfbb9e8d36bca07d678_2_690x387.png)](https://us1.discourse-cdn.com/flex022/uploads/ros/original/3X/2/9/2970bdeadc1a7726593c1bfbb9e8d36bca07d678.png "reservation")

_(a) Both robots request the same goal. (b) The orange robot is assigned the goal, while the blue robot is diverted to a parking spot._

Adding parking zones meant giving users another map element to configure, so I added support for defining them in [RMF Site Editor](https://github.com/open-rmf/rmf_site), the graphical tool used to create and edit Open-RMF site maps. Users can mark locations as parking zones, while existing floor polygons are treated as safe sets—the areas robots are allowed to enter. Alternatively, users can define both in YAML. The server publishes the loaded parking zones and safe sets as ROS messages for other nodes.

### [](https://discourse.ros.org/t/x/57646#p-117240-other-work-4)Other work

While working on the reservation logic, I found a grid-indexing bug affecting coordinates below zero. Fully negative regions were being checked as free but were not recorded as occupied, which meant two robots could receive overlapping goals in the negative quadrant. The [fix](https://github.com/arjo129/next_gen_prototype/commit/a9ad8e892a4204476af64c169ce7cddfaa445081) stores reservation cells in a sparse map keyed by signed coordinates, so negative positions are represented correctly.

The work also includes a web dashboard, unit tests, and ROS 2 launch tests covering three-robot diversion and cancellation.

## [](https://discourse.ros.org/t/x/57646#p-117240-h-2-layered-global-occupancy-map-5)2. Layered global occupancy map

**[PR #36](https://github.com/open-rmf/next_gen_prototype/pull/36)**, +7,867 / −114 across 78 files, 41 commits, merged 20 August 2026

Fleet navigation in `next_gen_prototype` happens at two levels. The central path server uses a global occupancy map to plan routes for all robots, and each robot then follows its assigned route with Nav2, using onboard sensors to avoid nearby obstacles. Before this work, observations from those sensors stayed in the robot’s local Nav2 costmap and did not update the global map. If robot A encountered a temporary blockage, such as a crowd filling a passageway, Nav2 could react locally, but the central path server still considered the passage clear and could send robot B down the same route. With a layered global map, robot A’s observation can be shared with the central path server, allowing robot B to take a more efficient alternative route before it reaches the blockage.

To share this information, I introduced a [common observation interface](https://github.com/open-rmf/next_gen_prototype/blob/feat/layered-global-map/discourse/3-layered-global-occupancy-map.md) for robots and other sensors to report free and occupied areas. Each observation records where it came from and how long it should remain valid. This allows the global map to combine reports from multiple sources and handle dynamic obstacles without retaining stale observations indefinitely. Observations can describe anything from a single obstacle point to a larger area and can come from LiDAR, depth cameras, or other sensors. Observations fall into two categories: clear (free space) and occupied. For example, in a LiDAR scan, the path of each beam is observed as clear, while a return at its endpoint may indicate an obstacle.

One subtlety is that different sensors may disagree about the same cell. For example, one robot may report it as free while another detects an obstacle there. To resolve this, we store observations separately by source rather than allowing one to overwrite the other. This keeps the interface flexible: instead of baking in one way to resolve conflicts, it leaves the fusion policy to the map server. The current implementation is conservative, keeping a cell occupied as long as any source has an active obstacle report. However, other policies can be added without changing the observation interface.

### [](https://discourse.ros.org/t/x/57646#p-117240-rasterization-optimization-6)Rasterization optimization

To keep map composition fast as observations accumulate, each incoming observation area is converted into occupancy-grid cells, or rasterized, once and stored by source. Those cells are then reused whenever the global map is updated instead of recalculating which cells each observation covers.

Before comparing performance, I confirmed that rasterizing observations during every composition and rasterizing them once on arrival produced identical maps. The benchmark covers overlapping observations from both stationary and moving sources.

| Scenario | Rasterize on composition | Rasterize on arrival | Speed-up |
| --- | --- | --- | --- |
| Stationary source | 34.9/s | 648.9/s | **18.6×** |
| Moving source | 34.7/s | 559.6/s | **16.1×** |

Both rolling cases improved by more than an order of magnitude.

### [](https://discourse.ros.org/t/x/57646#p-117240-replanning-7)Replanning

With the changes above, the path server uses the latest map whenever it generates a plan. However, updating the map does not automatically replace a route that a robot is already following because planning runs asynchronously. To close this gap, I extended the existing replanning flow so that changes to the global map can also trigger replanning for active routes. The plan executor compares the unfinished portion of each route with the latest global map. If a route stays blocked for 300 ms, it requests a new plan from the path server. The current plan remains active until the replacement arrives, at which point the executor switches the robot to the new route.

### [](https://discourse.ros.org/t/x/57646#p-117240-handling-observations-of-other-robots-8)Handling observations of other robots

Another issue is that robots can appear as obstacles in one another’s sensor data. When a robot moves on, the observing robot should clear its previous position instead of leaving a trail of false obstacles on the map.

[https://gist.github.com/user-attachments/assets/e20a62d0-1f2f-4d22-b6c7-e6136314ed12](https://gist.github.com/user-attachments/assets/e20a62d0-1f2f-4d22-b6c7-e6136314ed12)

_Incorrect behavior: the orange robot leaves a trail of false obstacles after passing through the blue robot’s sensor scan region._

To support this, a free-space observation clears earlier obstacle reports from the same source. Reports from other sources remain separate, so an obstacle another robot still detects is preserved. If no later observation clears a report, it expires after its configured lifetime. The cell then falls back to the static map and any remaining observations.

## [](https://discourse.ros.org/t/x/57646#p-117240-whats-left-10)What’s left

*   **A Rust Nav2 costmap observation node.** The demos currently create observation regions directly from raw LiDAR scans. A production node should read the robot’s local Nav2 costmap, apply a threshold, downsample the result, group adjacent occupied cells, and publish each group as a region. The current interface already supports adding this without changing existing message types.
*   **A configurable global planning grid.** PiBT, the grid-based multi-agent path planner used by the path server, currently downsamples maps to a hard-coded resolution of 1.0 m. Making this value configurable would allow it to be tuned for different environments. Further experiments could then determine a suitable default and assess whether smaller resolutions improve planning in tighter spaces without adding too much computational cost.
*   **Configurable blockage parameters** ([issue #46](https://github.com/open-rmf/next_gen_prototype/issues/46)). The debounce time, cooldown, and occupancy threshold are currently hard-coded and still need to be tuned for different robots.
*   **More observation formats.** Possible additions include delta grids that contain only changed cells, 3D voxel layers, semantic layers that attach meaning to map data, and a map-revision topic that identifies which version of the map was used to create a plan.
*   **Map names for observation regions** ([issue #5](https://github.com/open-rmf/next_gen_prototype/issues/5)). Observation regions from different levels cannot currently be distinguished, so multi-level maps are rejected.
